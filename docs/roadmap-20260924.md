# ChatNotes 功能拓展建议

日期：2026-09-24  
目标：把“网页对话采集→模型整理→本地笔记”逐步做成**能找到依据、能回答问题、能辅助模拟面试**的个人知识库。此文档以本次交付源码为基线，不把现有搜索误写成已经具备的 RAG 问答。

## 一、当前能力与产品方向

当前已经具备 ChatGPT/DeepSeek 的部分文本采集、会话原文、模型整理 Markdown、笔记编辑和回收站、全文与向量混合检索、单用户服务器同步。缺少可靠的导入恢复、可解释的冲突处理、引用式问答、面试会话和多平台可维护的采集适配。

建议把用户路径做成：

1. 采集和导入时明确展示平台、时间、是否完整、附件缺口与原始会话。
2. 检索时同时搜原文与笔记，让用户看到命中的段落和来源。
3. 问答时先检索，再让模型回答，逐条引用命中的原文或笔记；证据不足时明确说不知道。
4. 面试时围绕所选主题出题、追问、评分并引用知识库中的依据；记录本次表现供复盘。

## 二、实施优先级

| 顺序 | 要做的功能 | 最小可交付范围 | 验收标准 |
| --- | --- | --- | --- |
| P0 数据可信 | 服务端条件写入、冲突中心、导出后的导入恢复、服务器定期备份 | 每条笔记附服务端版本；冲突保留双版本并可选合并；ZIP 导入限制总大小、条目数与路径；数据库支持定期备份和恢复演练 | 两设备并发编辑不会静默覆盖；备份能在新安装恢复；恶意或损坏 ZIP 不污染已有库 |
| P0 可观测 | 同步状态页与采集健康页 | 显示上次成功时间、当前进度、失败原因、待处理冲突；每个会话标记来源与完整度 | 用户能区分“已采集”“部分采集”“同步失败”“仍在生成” |
| P1 检索体验 | 搜索结果按消息/段落定位、筛选、手动纠错 | 搜索平台、时间、分类、笔记/原文；点击直接打开命中段落；编辑笔记后只重建受影响的 chunk | 用固定问题集验证查准与查全；编辑后旧片段不再出现 |
| P1 引用式问答 | 单轮 RAG + 来源核对 | 查询→关键词/向量召回→去重/重排→模型回答；每条结论附笔记或会话消息 ID、段落和跳转入口；低证据分数则提示不足 | 能点开引用并核对原文；无法检索时不捏造出处；对比直接问模型的结果 |
| P2 面试助手 | 文字版模拟面试 | 选择岗位/知识主题/难度；出题、追问、用户作答、基于引用的反馈、会话保存和复盘 | 题目可追溯来源；用户回答与评分依据可复查；可继续上次面试 |
| P2 扩展采集 | 平台适配层、人工粘贴/文件导入 | 一个站点一个 adapter，分别解析请求、回复、历史、DOM；可手动粘贴文本并指定来源 | 平台页面改版时只影响对应 adapter；每个 adapter 有匿名合成协议样本回归 |
| P3 高级体验 | 语音面试、复习计划、跨端管理 | 语音输入/播放、错题复习、最小 Web 管理页、可选多用户权限 | 有明确的隐私、延迟、费用和设备兼容指标后再投入 |

**建议先完成 P0 再开始 P1 问答。** 如果底层数据不完整或同步会覆盖内容，问答引用再精美也无法让用户核对事实。

## 三、建议的技术演进

### 1. 统一知识条目与来源关系

保留原始会话作为事实来源，不直接把整理后的笔记当成唯一真相。新增或整理成以下实体：

| 实体 | 关键字段 | 作用 |
| --- | --- | --- |
| `source_message` | `platform, conversation_id, message_id, parent_id, role, captured_at, completeness, raw_text` | 保留分支、原文与采集缺口 |
| `note` | `note_id, title, category, markdown, source_message_ids, version, deleted_at` | 人工可编辑的整理结果 |
| `chunk` | `chunk_id, note_or_message_id, start/end, text_hash, embedding_model, embedding_version` | 精确索引、失效与引用定位 |
| `answer` | `question, answer_text, cited_chunk_ids, retrieval_run_id, created_at` | 问答结果与可重放的证据链 |
| `interview_session` | `topic, difficulty, turns, rubric, cited_chunk_ids, feedback` | 面试追问与复盘 |

不必立刻引入大型数据仓库或外部向量服务：单人小规模先沿用 SQLite FTS + 本地向量，测量索引体量和查询延迟后再决定是否迁移。年龄分布、偏好统计属于另一条分析链路，需在取得用户授权与定义保留周期后再建事件表和分析模型。

### 2. 检索与问答的最小闭环

- 查询预处理：保留原问题，同时可生成短检索词；不要改写掉专有名词。
- 召回：FTS 与向量各取一批候选，按稳定 chunk ID 融合，过滤已删、过期与低质量采集文本。
- 重排与预算：同一文档限制最大 chunk 数，避免一个长会话独占上下文；按引用质量选择模型输入。
- 生成：要求模型输出结构化 `answer + citations`；服务端/端上再校验每个 citation 是否在本次召回集合内。模型声称的引用不能直接当真。
- 界面：展示回答、引用片段、原始平台与“打开原文”；采集不完整的片段要带提示。
- 评估：准备 30–50 个你自己经常问的问题，逐条标出预期来源、是否应拒答；记录命中率、引用正确率、答案可用率和单次成本。

### 3. 平台适配与网页稳定性

把 `interceptor.js` 的平台分支拆成共享传输层、ChatGPT 适配器、DeepSeek 适配器以及未来新平台适配器。每个适配器保存匿名化的请求、流式事件、历史页面样本；端上保留 origin 白名单、主 frame 检查与失败后的人工核对入口。对 WebView 卡顿进行设备基准：区分页面自身、旁听脚本、数据库写入、渲染与网络，而不是凭主观感受归因。

### 4. 同步与安全

把当前 last-writer-wins 改为服务端版本条件写入（例如 `base_version`，不匹配时返回当前版本和冲突），同步状态与冲突原因在 UI 中可见。服务端按用户隔离文档、备份与 API Key；上线多用户前不要沿用一个全局 token。导入恢复与服务端备份需要单独的演练脚本和校验和。

## 四、建议的迭代顺序

1. **迭代 A：数据安全与可观测。** 完整构建/真机回归本次修复，加入版本条件写入、冲突中心、导入恢复、同步状态页和备份演练。
2. **迭代 B：检索质量。** 索引稳定 chunk ID、原文定位、筛选和固定评测集，确认检索确实能找到需要的答案依据。
3. **迭代 C：引用式问答。** 单轮 RAG、引用校验、低证据拒答、问题反馈与评测看板。
4. **迭代 D：文字模拟面试。** 先做题目、追问、反馈、复盘，再评估语音或跨端功能的投入。
5. **持续项：平台适配与性能。** 新增豆包/千问等平台时先取协议样本、合法访问方式与设备兼容验证，再编写适配器；每次页面变化保留回归样本。

## 五、决策检查点

- 在投入 RAG 前：确认原始消息与笔记能互跳，删除/编辑后索引一致，两设备同步无静默数据丢失。
- 在投入面试 Agent 前：确认问答引用正确率达到你能接受的标准；明确评分量表和“证据不足”的处理方式。
- 在投入多用户/云端分析前：明确数据所有权、访问控制、数据保留期限、模型调用成本与备份责任。

参考实现原则：Android WorkManager 的唯一任务/重试能力见 [Android 官方文档](https://developer.android.com/reference/androidx/work/WorkManager)；WebView origin 约束见 [Android 官方文档](https://developer.android.com/reference/androidx/webkit/WebViewCompat)；FTS 索引一致性参见 [SQLite FTS5 官方文档](https://www.sqlite.org/fts5.html)。
