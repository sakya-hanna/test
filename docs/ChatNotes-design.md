## 2. 产品目标与分期

目标是让用户能够输入“我以前问过的那个问题”，快速找到相关答案，并能返回原始对话核对，而不必记住笔记被分到哪个文件夹。

| 阶段 | 交付能力 | 是否依赖模型调用 | 验收重点 |
|---|---|---|---|
| 第一阶段 | 本地全文搜索、中文查询、结果摘要、筛选、来源跳转 | 搜索不依赖模型 | 能搜到、响应快、来源正确 |
| 第二阶段 | 同义问题匹配、语义检索、关键词与语义结果合并 | 可选 embedding 服务或本地模型 | 换一种问法仍能命中 |
| 第三阶段 | 根据已有资料回答问题，并引用证据 | 依赖选定的问答模型 | 回答有据可查，缺证据时明确说明 |

目录树保留为浏览方式；全局搜索成为主要入口。第一阶段可以单独发布，不能被向量数据库、云同步、知识图谱等后续能力阻塞。

当前不纳入首期：跨设备实时同步、自动联网补答案、多用户协作、自动合并删除旧知识、附件 OCR、语音知识抽取。以后确有需求再单独设计。

## 3. 用户流程与界面

### 3.1 首页与全局搜索

知识库首页提供明显的搜索框，提示语为“搜索问题、答案、关键词”。目录、最近更新、待整理项目作为辅助入口。

搜索默认覆盖全部有效知识，不被当前目录隐式限制。需要限制范围时，用户显式选择“当前分类”“指定会话”“指定时间”等条件，并始终看得见当前筛选项。

区分两种操作：

- **搜索资料**：返回已有内容，第一阶段完全在本地完成。
- **问知识库**：基于检索结果生成回答，在后续阶段开放；显示调用服务及计费提示，设置完成后不反复打断正常使用。

### 3.2 结果卡片

每条结果展示：标题、最相关的原始问题、答案命中片段、更新时间、来源平台与会话、必要的“内容未完整采集”标记。关键词高亮；分类只占辅助位置。

点击后直接定位到命中的段落或知识条目，并提供“查看原始问答”。相同笔记命中多个片段时默认合并为一张卡片，可展开其他命中位置。

没有结果时显示“未找到匹配的已保存资料”，提供清除筛选、换关键词等入口。不要把“索引尚未完成”“仅关键词模式”“向量服务不可用”混同为没有相关知识。

### 3.3 样例

| 输入 | 预期体验 |
|---|---|
| `WebView 白屏` | 优先命中曾讨论白屏原因及修复步骤的问答 |
| `网页为什么一聊天就很卡` | 首期通过分词与相关关键词召回；第二阶段补充同义表达匹配 |
| `怎么避免同名笔记被覆盖` | 命中独立 ID、版本保存、写入冲突相关资料 |
| `0x80004002` | 保留完整错误码进行精确匹配，不能被分词拆散 |
| `C++ 文件读写` | 同时支持自然语言和带符号的技术名词 |

这些是验收样例，不代表已确认当前知识库包含上述内容。

## 4. 数据结构：保留原文，增加检索索引

本次修复版已有 `ChatStore` 的 SQLite 原文、别名、请求和整理任务表，以及 `filesDir/notes` 的 Markdown。后续优先在此基础上增量迁移；如采用 Room，需显式接管或分离现有数据库并验证迁移，不能直接换库导致旧内容不可见。下表为目标模型，不表示修复版已经具备所有实体。

| 实体 | 关键字段 | 用途 |
|---|---|---|
| Conversation | 本地 ID、平台、外部会话 ID、标题、来源地址、采集状态 | 隔离不同来源及会话 |
| Message | 消息 ID、会话 ID、父消息 ID、角色、原文、状态、内容哈希 | 保存原始内容及分支，不被摘要覆盖 |
| KnowledgeItem | 稳定 ID、标题、类型、分类、标签、当前版本 ID、删除标记 | 表达可独立检索的知识条目 |
| KnowledgeVersion | 版本 ID、条目 ID、正文、生成方式、修改时间 | 保留编辑与重新整理的历史 |
| SourceRef | 知识版本 ID、原始消息 ID、可选片段位置、源内容哈希 | 回到真实证据；原文变化后检测失效引用 |
| Chunk | 片段 ID、知识版本 ID、顺序、正文、标题上下文、内容哈希 | 全文或语义检索的基本单元 |
| SearchIndex | 片段 ID、标题词项、问题词项、标签词项、正文词项 | 本地关键词索引 |
| Embedding | 片段 ID、模型标识、模型版本、维度、输入哈希、向量、状态 | 第二阶段的语义索引 |
| IndexJob | 任务 ID、目标版本、任务状态、重试次数、错误、检查点 | 可恢复的整理与索引任务 |

建立稳定 ID，不以模型生成的标题或文件路径作为主键。分类重命名不能改变知识条目 ID。

SourceRef 片段坐标需要明确单位，例如统一使用 Unicode 码点偏移；Android 展示时做转换。若偏移或哈希校验失败，退回显示整条原始消息，不能跳到错误位置。不要使用刷新后会变化的 DOM 顺序作为长期来源标识。

### 4.1 原始对话与分支

编辑问题、重新生成回复等分支必须保留关系。默认总结当前选择的分支，避免把互斥回答拼成一条线性对话。搜索原文时可以包含各个分支，并向用户说明匹配来自哪个版本。

原文、模型摘要、用户修订分别保存。模型回答本身不等于已验证事实；“用户确认”状态与检索相关度分开表达。

### 4.2 从旧 Markdown 迁移

1. 只读扫描现有文件，建立迁移清单及内容校验值，记录成功、失败和跳过原因。
2. 为每篇旧笔记分配持久 ID，将原目录映射为分类，保留原 Markdown。
3. 原文来源确实不存在的旧笔记标记“旧笔记，未关联原始问答”，不得凭空生成来源。
4. 迁移记录按原始文件身份与版本管理；不要仅凭内容哈希合并两份本来独立的笔记。
5. 元数据入库后异步建索引；迁移支持中断继续和重复执行，不重复创建条目。
6. 对账文件数、条目数、失败数、内容哈希。验证通过前不删除旧目录，不清空旧数据。

## 5. 第一阶段：可用的全文检索

### 5.1 技术选择与兼容性

建议沿用本地数据库。若采用 Room，其公开实体能力包含 FTS3/FTS4；不要假定目标设备系统 SQLite 都有 FTS5，也不要把 FTS5 的 `bm25()` 直接写进 FTS4 查询。最终选择必须由项目依赖、最低 Android 版本和设备能力决定。[Room FTS 文档](https://developer.android.com/training/data-storage/room/defining-data#fts)

如明确引入支持 FTS5 的 SQLite 实现，可评估其排序与分词能力，但需增加包体、版本与迁移测试。SQLite FTS5 的 trigram 检索具有短查询限制，不能把它当成对所有中文短词都有效的现成方案。[SQLite FTS5 文档](https://www.sqlite.org/fts5.html)

### 5.2 中文、英文和代码混合检索

- 对标题、原问题、答案、标签分别建立可加权的索引字段。
- 选用可离线运行且有测试覆盖的中文分词方案；索引端与查询端使用相同版本和规范化规则。
- 补充必要的中文字串召回策略，例如受控的双字词项，避免短词完全搜不到；评估索引膨胀和误匹配。
- 同时保留错误码、API 名称、文件名、带符号技术词的精确词项。不要把 `C++`、`C#`、`foo_bar` 等全部清成普通单词。
- 原文用于展示；规范化后的内容用于索引。不要为了分词修改用户原始文本。
- SQL 使用参数绑定。面向普通用户的查询不得未经处理直接解释为 MATCH 的复杂查询语法；引号、括号、减号、空输入都要测试。

### 5.3 排序与查询执行

首期采用可解释的字段权重：原问题和标题命中优先，其次标签、答案正文；时间只做次级排序，不能让最近的无关笔记排到前面。实际权重由人工标注的小型查询集调整。

输入防抖建议从 250–350 毫秒试起；查询在后台执行，新的查询取消旧任务。使用请求序号防止旧结果覆盖新结果。首屏分页返回约 20 条，不一次加载全部全文。

搜索结果立即来自已有索引。索引构建与网页采集不要共享一个可能被长任务占满的串行队列；分别限制并发和资源使用。

## 6. 第二阶段：语义与关键词混合检索

### 6.1 切分与向量

优先按标题、小节、问答对切分，保持代码块与步骤完整；超长段落再按长度切分。片段携带所属标题与必要上下文，避免单独一句“这样即可”失去含义。

切分长度由选定 embedding 模型的输入限制及中文语料效果决定，不固定照搬某个英文词数。可设置少量重叠，并用测试确认没有漏字、重复索引爆炸或拆断 Unicode 字符。

同一检索集合内的向量必须来自兼容的模型、版本和维度；不能直接混合不同模型向量计算相似度。更换模型后增量重建，旧关键词搜索保持可用。对返回向量验证维度、有限数值和数量。

如果调用远程 embedding 服务，应让用户知道哪些笔记将离开设备，提供范围选择和用量上限；没有配置服务时保留本地搜索能力。

### 6.2 检索管线

1. 统一处理查询与显式筛选条件。
2. 并行取得关键词候选与语义候选。
3. 使用基于排名的融合方法，例如 RRF，避免直接相加两个不同量纲的分数。
4. 合并同一笔记的重复片段，保留最相关段落。
5. 根据标注集评估是否需要重排；不默认增加一次昂贵模型调用。
6. 返回卡片、命中片段和来源。语义相关度不显示为事实正确率。

个人小规模数据可先评估本地向量扫描的延迟与内存；规模增长后再选择有 Android 支持和迁移方案的索引实现。不要在没有实测规模的情况下强行引入服务器向量数据库。

## 7. 第三阶段：有来源的知识库问答

问答前先检索，仅把获选证据和明确的来源 ID 发送给模型。不得每次把整个知识库拼入提示词。

模型输出结构化的答案段落及所引用的证据 ID。应用校验 ID 是否属于本次检索结果，展示可点击引用。引用存在不代表内容一定准确，仍应允许用户展开原文核对。

来源不足、彼此矛盾或采集不完整时，回答应直接说明；必要时提出一个澄清问题。找不到资料时，显示“已保存资料不足以回答”，不能把模型常识冒充知识库中已有的结论。

若未来增加“用通用知识补充”开关，必须单独标注补充部分，并与来自个人知识库的证据分开。

知识片段按不可信数据处理：模型不能执行笔记中夹带的指令。生成回答默认不自动写回知识库，避免未经核实的回答被反复检索和自我强化。

## 8. 索引一致性与任务恢复

保存笔记、建立检索索引、生成向量是不同状态。界面应能显示“原文已保存”“笔记已保存，待索引”“关键词可查，语义索引等待中”等实际状态。

创建、编辑、删除、恢复知识条目时，都需要同步更新相关索引、向量和缓存。删除旧版本后，不得继续在问答中引用该版本。重建过程采用索引版本或切换标记，避免把半套新索引暴露给查询。

任务持久化并以内容哈希、模型版本及片段 ID 实现幂等。长任务保存检查点；临时网络故障有限重试；配置错误、权限错误和无效模型输出不无限重试。WorkManager 可用于要求离开页面或进程结束后恢复的持久任务，但不是对即时执行时机的保证。[Android 持久后台任务文档](https://developer.android.com/develop/background-work/background-tasks/persistent)

取消操作应尽力终止网络请求，并说明已经发出的远程请求可能仍产生费用。凭据不进入任务输入、日志或导出文件。

## 9. 网页卡顿、页面错乱：已确认缺陷与待验证原因

第 1 节列出的原生构造器语义破坏和主线程日志是本次已修复的直接代码缺陷。Worker 的第二参数决定 classic/module 类型，丢弃它会改变脚本加载语义。[Worker 构造器说明](https://developer.mozilla.org/en-US/docs/Web/API/Worker/Worker)

页面是否仍有错位，需进一步区分 Android 主线程、WebView 渲染进程、注入脚本、页面布局和网络服务端。修复版保持实际 UA、默认网页布局，不注入 CSS 修补站点。下面列出后续真机定位表，其中可能与已修问题重叠，不能把所有项目都当作已证明根因。

| 待验证假设 | 常见表现 | 需要的证据 | 确认后的处理方向 |
|---|---|---|---|
| 主线程执行文件扫描、数据库写入、重型 JSON/Markdown 处理 | 输入、滚动及原生按钮同时迟缓 | 主线程 trace、磁盘访问、各阶段耗时 | 移到后台，分页，避免阻塞采集队列 |
| 每个 token 都跨桥接通信并重绘 UI | 一生成回复就明显变卡 | 每秒事件量、事件大小、原生更新次数 | 合并增量更新、节流，结束与中断时强制提交最后进度 |
| 重复包装 fetch 或重复安装观察器 | 随页面切换逐渐变慢、消息重复 | 单页面安装计数、活动 reader/observer 数 | 幂等注入，明确页面与会话生命周期 |
| 全页面高频 DOM 扫描触发布局计算 | 生成长回复、滚动历史时卡顿 | JS Performance trace、Layout/Recalculate Style 次数 | 缩小观察范围、合并变更、移除高频全量 innerText 扫描 |
| 克隆响应或队列没有边界 | 聊天越久内存越大，后台返回后白屏 | 两端消费速率、队列长度、渲染进程内存 | 有界观察与缓冲，只取消旁路，不破坏网页原始响应 |
| 强制 UA、CSS、缩放或 viewport 设置不适配 | 排版重叠、字号异常、横向溢出 | 默认设置与当前设置对照 | 按证据撤销具体覆盖项，不凭猜测批量改设置 |
| 键盘、系统字体、窗口 Insets 处理错误 | 输入框被挡、上下留白、旋转后错位 | 键盘前后视口尺寸、布局层级、字体比例 | 统一原生窗口和网页视口策略，分别测试 |
| WebView 或 Activity 生命周期不正确 | 切 Tab/回前台反复刷新，输入丢失 | 实例数量、loadUrl 调用次数、创建销毁日志 | 稳定页面实例，恢复已保存状态，避免无条件重新加载 |
| 渲染进程退出后仍复用旧实例 | 白屏后长期无法恢复 | 渲染进程退出回调、内存与崩溃记录 | 丢弃失效 WebView，提供恢复入口，保留原文和会话地址 |
| 网页接口、资源、认证或传输异常 | 原生界面正常，但回复断开或组件缺失 | 状态码、控制台、资源加载、同环境浏览器对照 | 针对失败链路处理；不绕过 TLS 校验或认证限制 |

Android 官方提供 WebView 远程调试与控制台工具，可检查真实 DOM、CSS、JavaScript 和资源错误。[WebView 调试文档](https://developer.android.com/develop/ui/views/layout/webapps/debugging)

卡顿应以 trace 和帧耗时判断；渲染预算受设备刷新率影响，不用单一“感觉更流畅”替代测量。[Android 渲染性能文档](https://developer.android.com/topic/performance/vitals/render)

### 9.1 对照实验

同一设备、网络、字体设置、输入脚本和相近热状态下测试：

- A：系统 Chrome 中访问同一平台。
- B：最小 WebView，默认兼容设置，关闭采集。
- C：B 加入网络观察，但关闭 DOM 补采集及额外 UI 更新。
- D：完整应用。

A 与 B 的差异用于识别宿主/渲染兼容性；B 与 C 用于评估拦截开销；C 与 D 用于定位原生保存、观察器和界面更新。差异只是证据线索，要结合日志和 trace 验证。

场景覆盖短会话、长会话、代码块、表格、公式、持续流式输出、反复切 Tab、键盘开关、旋转、前后台、弱网与重连。记录系统版本、WebView 包及版本、应用版本、峰值内存、慢帧比例、桥接速率、保存队列及渲染异常。

调试能力仅在调试构建启用。日志不记录 Cookie、Authorization、API Key 或完整对话；必要的诊断包由用户主动导出。

### 9.2 实现边界

- 支持明确的网页来源和消息来源；外部站点不继承采集权限。
- 不绕过证书错误，不自动清空 Cookie 作为通用修复。
- 页面协议不受支持时显示采集不完整，不保持误导性的“全部已保存”。
- 捕获失败不得破坏网页原始响应、AbortSignal、状态码和读取行为。
- 崩溃恢复不能自动重发用户提问，避免重复生成和重复计费。
- 设置“关闭采集继续浏览”的应急模式，并清楚标记该时段没有自动归档。

### 9.3 如果内嵌网页仍不能达到稳定性要求

| 方案 | 浏览能力 | 对话采集边界 |
|---|---|---|
| 继续优化 WebView | 可控制内嵌体验，但需持续适配站点 | 可观察受支持页面，必须检测协议变化 |
| 系统浏览器 / Custom Tabs | 更多交由用户浏览器处理 | 不能假设应用可读取浏览器任意 DOM、Cookie 或网络流；需设计主动分享、复制或导入 |
| 原生模型 API 对话 | 应用可以控制请求、界面和保存 | 属于独立 API 使用流程，不能假定等价于 ChatGPT 网页订阅或已有会话 |

近期先定位现有 WebView 问题，再根据实测决定是否增加可选浏览方式。

## 10. 验收标准

以下是建议的验收目标，不是已测得成绩；实施前应固定测试设备、语料与统计方法。

| 能力 | 必须验证 |
|---|---|
| 数据安全 | 升级和迁移后旧笔记可读取；中断可继续；重复迁移不重复导入；不破坏原始内容 |
| 本地检索 | 中文短词、同名标题、错误码、API 名、符号、空输入、无结果和混合语言均可正确处理 |
| 查询并发 | 快速连续输入时，只显示最新查询结果；取消旧查询有效 |
| 索引一致性 | 新增可查、编辑后更新、删除后不可召回、重建中不混用失效结果 |
| 来源跳转 | 每条引用能找到确切版本及消息；失效引用显式提示 |
| 语义检索 | 换一种问法的标注查询有明确改进；不同模型向量不混用；服务不可用时关键词仍可用 |
| 知识库问答 | 无证据时不编造库内答案；矛盾与不完整内容有提示；引用 ID 均通过校验 |
| 搜索性能 | 先在约 1 万条笔记的固定数据集测首屏延迟，初始目标 P95 ≤ 500ms，再按设备能力调整 |
| 网页稳定性 | 30 分钟固定交互脚本下无新增崩溃/ANR；相对关闭采集的基线评估内存增长和慢帧，而不是只看一次启动 |
| 恢复与费用 | 断网、进程结束、取消及重试不丢原文；已完成分段可复用；无无限重试或静默重复调用 |

建立至少 30 个有人工相关性标注的查询，包括至少 10 个中文改写问题。记录 Recall@5、首个相关结果排名、无结果率和延迟，避免只看个别成功例子。

## 11. 后续实施顺序

1. 用同一签名覆盖安装本次修复源码构建的 APK，保留原应用数据；不要卸载重装来规避问题。
2. 执行源码包中的设备验收清单，核对登录、原文保存、再次整理、旧笔记读取及网页稳定性。
3. 若设备仍发生错位或卡顿，按第 9 节收集可定位的数据，再作针对性修复。
4. 用户授权功能开发后，单独实施第一阶段全文搜索与来源跳转。
5. 根据查询集评估，再推进语义检索和知识库问答。

后续打包源码 ZIP 应继续包含 `app/src/`、模块和根项目 Gradle 配置、`settings.gradle(.kts)`、`gradle.properties`、`gradlew`/`gradlew.bat` 与 `gradle/wrapper/`；如果存在其他模块、version catalog 或 buildSrc，也一并保留。不要包含 API Key、签名私钥、`local.properties`、设备日志里的敏感内容或无关构建缓存。
